# 设备验证

1. 在连接设置中只填写后端地址（例如 `http://192.168.1.20:7345`）。加密方式与公钥不能手动填写、粘贴或通过二维码导入。
2. 点击「设备验证」。客户端显示 `XXXXX-XXXXX` 验证码和后端传输公钥的指纹（`XXXX-XXXX-XXXX-XXXX`）。在后端 TUI 按 `d` 打开设备验证，选择对应申请，核对双方完整的验证码（指纹也显示在旁边）。
3. 按 `a` 批准，或按 `r` 拒绝。设备名称由客户端自报，核对时以验证码为准。
4. 批准后后端登记此设备的签名公钥，并在加密的登记结果里回传本次申请所用的传输加密方式与公钥。客户端核对它们与申请时收到的完全一致后，一次性写入设备密钥、加密方式、公钥和「已验证」标记，然后自动连接。任何一项不一致都不会保存。

验证码由包含传输加密方式与公钥的握手内容算出，所以核对验证码同时核对了将被固定的公钥：中间人替换公钥会得到不同的验证码。

「设置」中只读显示当前后端的加密方式、公钥指纹与验证状态，并提供「重新配对」。重新配对同一个后端（规范化后同一地址）沿用已有的设备密钥，设备 ID 与历史密钥接收方保持不变；只有该地址还没有设备密钥时才生成新的。修改后端地址会清除设备密钥、加密方式、公钥与验证标记；新增的后端也不会继承它们。

申请有效期为 5 分钟，可在客户端取消。切换后端或修改地址会取消当前申请；过期、拒绝、取消以及领取过的申请不能再次领取结果。

此功能需要同时更新后端和客户端：设备验证使用配对 v3，传输使用 transport v2，旧后端会被提示升级。TUI 保存加密设置后会重启正在运行的 daemon，使新要求生效。

## 传输加密（transport v2）

规格见后端 `docs/transport-v2.md`，实现在 `TodeX_protocol` 的 `secureChannel.ts` / `secureTransport.ts`。

- 经设备配对验证并固定了加密方式与公钥的后端，客户端一律走 transport v2，回环地址也一样：WebSocket 用 `tv=2` 握手并收发二进制密文帧，所有 REST 请求（包括 `/v2/version`）都封装进 `POST /v2/sealed` 隧道。只有 `/health` 与 `/v2/transport-policy`（都不含密钥或业务数据）直接请求；设备验证（`/v2/device-pairing/*`）发生在固定公钥之前，同样直接请求。
- 没有固定公钥时，只能连接回环地址（`localhost`、`127.0.0.1`、`::1`）上加密方式为 None 的后端，并使用明文。连接其他地址会被拒绝，并提示先在「设置 → 设备验证」完成配对。客户端不会因为后端声明 None 而降级为明文；远程地址的配对申请若收到 None 也会被拒绝。
- 已保存了公钥但没有经设备配对验证的档案（旧版本手动导入的公钥）在任何地址（包括回环）都会被拒绝，并提示重新配对，不会退回明文。
- 每次连接先读取 `/v2/transport-policy`：后端要求的加密方式与配对时固定的不同（包括后端改为 None）时提示重新配对；后端没有声明 `transportVersion: 2` 或 `sealedRevision: 2` 时提示升级后端，不回落；已保存的公钥无法使用时提示重新配对。
- REST 隧道为第 2 版：请求带 `X-Todex-Sealed-Revision: 2`；响应必须是 `200` 且 `Content-Type: application/vnd.todex.sealed; r=2`，正文以 32 字节响应随机数开头，客户端用它为每个响应派生新的下行密钥。不带 `r=2` 的加密响应表示后端过旧，提示升级后端；其他未加密的回答一律按未认证的普通请求失败处理。
- 隧道内的 `503 TRANSPORT_BUSY`（后端保证请求未执行）等待 `Retry-After`（最多 5 秒）后用新签名重试一次；`401 AUTH_TIMESTAMP_REJECTED` 按错误中的 `serverTime` 记录该后端的时钟偏差，之后签名都用本地时间加偏差，并立即重签重试一次。只有加密隧道内（或回环明文）的回答才会被采纳。
- 新的加密 WebSocket 先往返一次 `server.ping` 才显示已连接。公钥不对时后端以 `4400 transport crypto failure` 关闭连接，REST 隧道返回 `400 TRANSPORT_CRYPTO_FAILED`；客户端提示后自动重连，反复出现时应重新配对。
- 发送前按明文检查 8 MiB 帧限制（减去 24 字节帧开销），过大的消息在加密前就被拒绝，不消耗计数器。

## 实现边界

批准入口只读取和写入后端本机的私有控制目录，没有公网批准 API。网络上的申请、揭示、查询和取消请求有大小、数量及频率限制。

设备验证使用配对 v3（先承诺、后揭示）：客户端为单次申请生成临时 X25519 密钥与 32 字节随机数，`create` 只提交二者的 SHA-256 承诺；后端返回本次申请的公钥后，客户端再通过 `reveal` 公开临时公钥与随机数，后端核对承诺后才在 TUI 显示验证码。这样中间人无法在看到后端公钥之后挑选自己的密钥去碰撞验证码。`create` 必须带 `transportBinding: 1`（否则后端返回 `426`），响应附带 `transportProtocol` 与 `transportPublicKey`；客户端在派生任何内容之前校验它们（协议名、规范 base64url、长度、可完成握手；None 只接受回环地址）。`create` 还必须带 `deviceNameBinding: 1`：设备名先在客户端规范化（去掉控制字符与双向控制字符，去掉首尾空白，最多 80 个 Unicode 字符，为空时用默认名），后端只校验不改写。握手内容在原有字段之后追加长度前缀的加密方式、公钥原始字节与 UTF-8 设备名，双方从同一 v3 握手内容计算验证码，因此 TUI 显示的设备名也被验证码覆盖；后端批准后用 HKDF-SHA256 派生的密钥和 XChaCha20-Poly1305（以完整握手内容为附加数据）交付登记结果 `{deviceId, transportProtocol, transportPublicKey}`，只有发起申请的客户端能够解密。

等待批准期间，查询遇到 `429`、`5xx` 或网络错误时把间隔翻倍（最多 5 秒）继续查询，直到申请过期；只有 `404`、`401`、被拒绝、已过期或用户取消才结束。

吊销此设备后，需要重新验证设备。登记结果的响应丢失时，需要重新申请。

## 历史记录加密

会话历史始终以端到端密文保存（后端只有 `e2e` 模式，没有开关），只有登记过的设备与恢复密钥能读取（规格见后端 `docs/history-encryption.md`）。

- 客户端连接后端时为该后端生成一把历史密钥（X-Wing 种子）并通过 `history.recipient.register` 登记公钥。桌面端用系统钥匙串（Electron safeStorage）加密种子；没有可用密钥服务的 Linux 桌面会拒绝保存而不是明文落盘。请求签名用的设备密钥同样由系统钥匙串加密保存；旧版本留下的明文副本在启动时迁移并删除，迁移失败时保留明文并报错。
- 「设置 → 历史记录加密」显示可读取历史的密钥（此设备、其他设备、恢复密钥），可吊销其他密钥。尚未设置恢复密钥时，此处与对话上方的提示条都会警告「所有设备丢失后历史将无法解密」；「立即设置」会展示 24 个 BIP39 英文单词与二维码作为恢复密钥，确认已保存后才上传其公钥。提示条关闭前需二次确认，关闭状态按后端记住。
- 写入时后端没有可加密的接收方（`HISTORY_KEY_REQUIRED`）时，客户端提示「本设备尚未登记历史密钥」并重新登记一次。
- 加密之前保存的旧对话带 `legacyPlaintext`，只读：对话顶部显示「旧版未加密历史，只读」，输入框、重试、排队、压缩、fork、改名、权限应答与运行控制均不可用；仍可查看、导出、归档与删除。列表项带锁形标记；后端对这类写入返回 `HISTORY_READ_ONLY`。
- 新设备只能读取登记之后写入的历史。点「请求访问旧历史」后，在已授权设备的同一面板点「授权」，客户端会逐批取回自己的封装、解开后为新设备重新封装并上传；中断后可继续。
- 导入恢复密钥（24 个单词或二维码文字）等同一次自授权，之后此设备即可读取恢复密钥覆盖的历史；恢复密钥本身不会保存。
- 只有 `/v2/version` 报告 `historyEncryption: 1` 的后端会显示此功能；授权请求与授权结果都不推送：重连与打开设置面板时会重新读取；本机有待处理的授权请求时每 15 秒查询一次，授权完成后无需刷新即解锁已显示的历史。此设备的密钥被吊销后无法再次登记，客户端会生成新密钥重新登记，旧历史需重新授权或导入恢复密钥。
- 无法解密的历史显示为「此设备尚未获授权查看这段历史」，不影响其余内容；`/retry` 会附带本机解密出的原始消息。
